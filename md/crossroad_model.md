# Модель перекрёстка: соглашения и план работ

Документ фиксирует всё, о чём мы договорились, что уже реализовано и что остаётся сделать. Обновляется по мере работы.

## 1. Цель

Построить макроскопическую модель перекрёстка и оптимизировать настройки светофора. Метрики:

- пропускная способность при заданных фазах светофора;
- среднее время ожидания;
- минимальные длительности фаз, которые обеспечивают требуемую пропускную способность по каждому направлению.

Главная цель оптимизации: сократить фазы светофора, чтобы уменьшить ожидание, но не допустить пробок.

Модель должна быть универсальной: параметры перекрёстка задаются конфигурационным файлом, а не зашиты в код. Приоритет трамвая на этом этапе не рассматривается.

## 2. Принципы проекта

1. **Расчётные модули** (`cr_capacity.js`, `cr_cycle.js`) — чистые функции:
   - нет ввода-вывода;
   - нет собственных данных и значений по умолчанию, всё приходит аргументами;
   - не вызывают друг друга и вообще ничего не импортируют;
   - не зависят от Node, поэтому их можно подключить на веб-странице;
   - сами проверяют свои входные данные и при ошибке бросают понятное исключение.
2. **Модуль запуска** (`crossroad_model.js`) — единственное место, где есть ввод-вывод и сборка данных: чтение конфигурации, построение таблиц, кеш, отчёт. Он вызывает расчётные модули и передаёт данные от одного к другому. На верхнем уровне в нём только импорты и глобальные переменные (пути к файлам), весь код в функциях.
3. **Исходных данных один источник:** `crossroad_config.json`.
4. **Расчётные данные** хранятся в отдельных файлах и не содержат никаких исходных данных, только результаты расчёта.
5. **Кеш** работает по простому правилу для каждой функции вида `getXxx(config, rebuild)`:
   - `rebuild = false`: пытаемся прочитать данные из файла;
   - не получилось или `rebuild = true`: считаем, сохраняем в файл;
   - возвращаем данные.

   Никаких сравнений файла с конфигурацией нет. После изменения конфигурации или расчётных модулей нужно вызвать функцию с `rebuild = true`. Новые расчётные данные добавляются такими же функциями со своим файлом.
6. **Файла `package.json` в проекте нет.** Node 22.7+ (и 20.19+) сам определяет ES-модули в `.js` по синтаксису. В старых версиях нужен флаг `--experimental-detect-module`. В браузере файлы подключаются как `<script type="module">`.

## 3. Пример: исходный перекрёсток

**Геометрия**

- Главная дорога: 2 полосы в каждую сторону, посередине аллея около 10 м. Машины аллею не пересекают, она разделяет направления.
- Главную дорогу пересекают трамвайные пути.
- Рядом с трамвайными путями проходит автомобильная дорога: 1 полоса в каждую сторону. В своей фазе она открывает движение в обе стороны одновременно.
- Аллея прерывается в местах пересечения с трамвайными путями и пересекающей дорогой.

**Фазы светофора**

| Фаза | Что едет | Зелёный, с | All-red после, с |
|------|----------|-----------|------------------|
| 1 (`main_a`) | Сторона А главной дороги: сначала трамвайные пути, потом дорога | 55 | 0 |
| 2 (`main_b`) | Сторона Б главной дороги: сначала дорога, потом трамвайные пути | 25 | 0 |
| 3 (`minor_tram`) | Трамвайные пути и пересекающая дорога | 25 | 5 |

- После каждого зелёного идёт жёлтый 5 с. В таблицах хранится только зелёный.
- All-red 5 с стоит только после фазы 3. Он нужен, чтобы трамваи и машины, начавшие пересекать главную дорогу на жёлтом, успели освободить проезжую часть. После жёлтого главной дороги all-red не нужен.
- Длина цикла: (55+5) + (25+5) + (25+5+5) = 125 с.

## 4. Подход к моделированию

- Модель макроскопическая. Физику разгона колонны считаем один раз и сохраняем в таблицу «секунды зелёного → число проехавших машин». Дальше расчёт и оптимизация используют только таблицу.
- Интенсивность движения не является входом модели: главное в ней настройки светофора, они определяют, сколько машин может проехать.
- Среднее ожидание считаем при предельном (насыщенном) потоке: за цикл подъезжает ровно столько машин, сколько фаза успевает пропустить. Это характеристика плана светофора, а не реального трафика.
- Любая непроехавшая за фазу машина считается проблемой (пробкой). Перенос остатка очереди между циклами не моделируем: для этого пришлось бы знать периодичность поступления машин с разных направлений, а мы моделируем один светофор.
- Адаптивная система (подстройка фаз под интенсивность) проектируется отдельно, на следующем этапе.

## 5. Файлы проекта

| Файл | Назначение |
|------|------------|
| `cr_capacity.js` | Модуль A: физика разгона очереди, таблицы N → M. Расчётный, без ввода-вывода и данных. |
| `cr_cycle.js` | Модуль B: проверка конфигурации цикла, расчёт плана светофора, поиск минимального плана. Расчётный, без ввода-вывода и данных, без импортов. |
| `crossroad_model.js` | Модуль запуска: чтение конфигурации, построение таблиц, кеш, отчёт. |
| `crossroad_config.json` | Единственный источник исходных данных. |
| `cr_tables.json` | Расчётные таблицы пропускной способности. Создаётся автоматически. |
| `crossroad_model.md` | Этот документ. |

**Запуск** (из папки проекта):

```
node --input-type=module -e "import { main } from './crossroad_model.js'; await main();"
node --input-type=module -e "import { main } from './crossroad_model.js'; await main({ rebuild: true });"
```

Вторая команда пересчитывает таблицы, не используя кеш. Из своего кода: `import { loadConfig, getCapacityTables, main } from './crossroad_model.js'`.

## 6. Конфигурация (`crossroad_config.json`)

Формат разделов описан в шапках модулей. Модуль B использует `signal`, `laneGroups`, `phases`, `optimization`, `demandVehPerHour`. Остальное читает `crossroad_model.js`.

- `signal`: `yellowS`, `greenMinS`, `greenMaxS` (целые секунды; диапазон зелёного он же диапазон таблиц).
- `vehicle`: параметры машин. Задаются все, значений по умолчанию нет. Состав: время реакции, ускорение, замедление, длина, отступ первой машины от линии (каждый со своим разбросом), доля длины для зазора между стоящими машинами `standingGapFraction` (0.6667, то есть около 2/3), нештрафуемый порог. Неизвестные и пропущенные ключи считаются ошибкой.
- `laneGroups`: группы полос, получающие зелёный одновременно (`speedLimitKmh`, `lanes`; `name` для читателя). Для пересекающей дороги с одновременным движением в обе стороны `lanes` = 2.
- `phases`: фазы по порядку цикла (`id`, `name`, `laneGroup`, `greenS`, `allRedAfterS`). Несколько фаз могут ссылаться на одну группу и используют одну таблицу.
- `tables`: `trials` (число прогонов) и `seed`. С числовым `seed` таблицы воспроизводимы, с `null` случайны.
- `optimization.greenStepS`: шаг сетки зелёного при поиске минимального плана.
- `demandVehPerHour`: необязательно, требуемая пропускная способность по фазам, машин/час.

## 7. Расчётные данные (`cr_tables.json`)

Только результаты расчёта: `{ "<id группы>": [ { greenDurationS, mean, min, max, p5, p95 }, ... ] }`. В файле нет параметров машин, скоростей, числа полос, числа прогонов и seed. Идентификатор группы нужен как ссылка на конфигурацию, `greenDurationS` — ось таблицы.

Читает и пишет файл только `crossroad_model.js` (функция `getCapacityTables`), расчётные модули получают таблицы аргументом.

## 8. Модуль A (кратко)

Параметры машин приходят снаружи (в примере: реакция 1.3 с ±35%, ускорение 2.5 м/с² ±25%, замедление 3.5 м/с² ±25%, длина 4.5 м ±15%, отступ первой машины от линии 1 м ±30%, скорость водителя = лимит + случайно от 0 до 20 км/ч). Разбросы равномерные.

- Очередь стоит с зазором 0.6667 длины (около 2/3), первая машина трогается через свою реакцию после начала зелёного, каждая следующая через свою реакцию после предыдущей (каскад). Момент проезда: передний бампер пересёк стоп-линию.
- Дилемма-зона: к концу зелёного непроехавшая машина проезжает, если не может остановиться (`v·t_реакции + v²/(2·замедление)` больше остатка) и успевает до конца жёлтого. Первая непроехавшая машина блокирует всех позади.
- Для каждого N по K прогонов Monte-Carlo, хранится среднее, min, max, p5, p95.
- Модуль сам проверяет параметры (`validateParams`) и входные данные: пропущенный параметр, неизвестный ключ или недопустимое значение дают исключение со списком проблем.
- Упрощения v1: нет ограничения следования между машинами (формула зазора в движении не применяется), нет штрафа за повороты, трамваи не моделируются, один усреднённый тип машины.

## 9. Модуль B: расчёт цикла

**Длина цикла:** C = Σ (зелёный + жёлтый + all-red) по всем фазам.

**Пропускная способность фазы:** за цикл M(g) из таблицы (среднее, p5, p95), за час M(g)·3600/C. Итог по перекрёстку считается только по среднему: сумма перцентилей фаз не равна перцентилю суммы.

**Ожидание при насыщенном потоке:**

1. Из таблицы оценивается поток насыщения s (наклон M(N) на верхней половине таблицы) и потери на старте.
2. Эффективный зелёный g_e = M(g) / s.
3. Среднее ожидание на машину фазы d = (C − g_e) / 2 (формула равномерной задержки Вебстера при степени насыщения 1, прибытие равномерное).
4. Для перекрёстка берётся среднее по фазам с весом по числу машин.

**Функции:**

- `validateCycleConfig(config)` — проверка разделов конфигурации, которые использует модуль.
- `evaluatePlan(config, tables, greensOverride)` — показатели плана; `greensOverride` позволяет оценить другие зелёные без правки конфигурации.
- `findMinimalPlan(config, tables, demandVehPerHour, options)` — самые короткие зелёные на сетке (шаг `greenStepS`), при которых каждая фаза пропускает требуемое число машин в час. Требуемое число за цикл зависит от длины цикла, поэтому решается итерацией от минимальных зелёных. Результат либо план, либо указание фазы, для которой требование недостижимо. `options.statistic`: `mean` (по умолчанию), `p5` (консервативно) или `p95`.
- `lookupVehicles`, `fitSaturation`, `cycleLengthS`.

## 11. Принятые решения

1. All-red только после фазы 3, 5 с.
2. После каждого зелёного жёлтый; длина фазы = зелёный + жёлтый + all-red.
3. Основная цель оптимизации: сократить фазы, чтобы уменьшить ожидание без пробок. Оптимизация будет строиться по разным параметрам.
4. Метрики по перекрёстку: пропускная способность для заданных фаз и минимальное время (зелёные), обеспечивающее требуемую пропускную способность по направлениям.
5. Пересекающая дорога в своей фазе работает в обе стороны одновременно (`lanes` = 2).
6. Остаток очереди не переносим: непроехавшая машина означает пробку.
7. Принципы проекта из раздела 2: чистые расчётные модули, один конфиг, файлы расчётов без исходных данных, простой кеш по `rebuild`, без `package.json`.

## 13. Открытые вопросы

1. **Критерии оптимизатора.** Какие именно ограничения и веса нужны помимо «минимальный план под спрос»: фиксированная длина цикла, равенство ожидания по направлениям, минимизация среднего или максимального ожидания.
2. **Требуемая пропускная способность по направлениям.** Реальные значения спроса для примерного перекрёстка (сейчас в конфигурации спрос не задан).
